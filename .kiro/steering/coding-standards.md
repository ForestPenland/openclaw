# Coding Standards

## Language Conventions

- **TypeScript** for adapters (`adapters/`), agents (`agents/`), and scripts (`scripts/`)
- **Python** for Lambda handlers (`lambdas/`), CDK infrastructure (`infra/`), and operational scripts (`scripts/*.py`)
- CDK stacks use Python 3.12+ with `aws-cdk-lib` as the sole CDK dependency

## Project Structure

```
adapters/          — TypeScript modules injecting AWS services into OpenClaw
agents/            — Supervisor and specialist agent implementations
lambdas/           — Python Lambda function handlers
infra/
  stacks/          — One CDK stack per concern
  constructs/      — Reusable CDK constructs
  app.py           — CDK app entry point
  requirements.txt — Python deps (aws-cdk-lib only)
scripts/           — Operational and build scripts
workspace-seeds/   — Default workspace file templates
tests/
  unit/            — Unit tests (vitest for TS, pytest for Python)
  property/        — Property-based tests (fast-check for TS, hypothesis for Python)
```

## Git Workflow

- Branch: `feature/aws-extension`
- Always use `--no-verify` on git commits — upstream OpenClaw has strict pre-commit hooks (linting, formatting, architecture checks) that don't apply to our extension code
- Commit message format: `type: description` (e.g., `feat: add Bedrock provider plugin`, `fix: handle missing Telegram secret`, `docs: update DEPLOYMENT.md`)

## CDK Conventions

- One stack per concern — don't combine unrelated resources
- Stack names: `OpenClaw<Purpose>` (e.g., `OpenClawGateway`, `OpenClawStorage`)
- Cross-stack references via constructor parameters, not SSM lookups
- All S3 buckets: `BlockPublicAccess.BLOCK_ALL`
- All DynamoDB tables: `PAY_PER_REQUEST` billing
- Don't hardcode CloudWatch log group names — let CDK auto-name them
- Exclude `infra/` from Docker asset staging to avoid ENAMETOOLONG

## Testing

- TypeScript tests: `vitest` for unit tests, `fast-check` for property tests
- Python tests: `pytest` for unit tests, `hypothesis` for property tests
- Always test config changes against OpenClaw's validation before deploying (the Gateway validates `openclaw.json` at startup)
- Property tests: minimum 100 iterations per property

## Configuration

- Secrets go in AWS Secrets Manager under `openclaw/` namespace
- Environment variables are set in `gateway_stack.py` on the container definition
- Runtime config is generated by `scripts/configure-gateway.mjs` → `~/.openclaw/openclaw.json`
- Never hardcode secrets or tokens in code or CDK stacks

## Docker

- Base image: `node:24-bookworm` (needs AWS CLI, can't use slim)
- Multi-stage build: build stage + runtime stage
- Use `--no-frozen-lockfile` for pnpm install
- Use `CI=true pnpm prune --prod --config.frozen-lockfile=false` for dev dep removal
- Entrypoint: `docker-entrypoint.sh` (S3 sync → configure gateway → start)
