# Requirements: Dynamic Execution Environments

## Introduction

This document defines the requirements for a dynamic execution environment system that enables the OpenClaw agent to intelligently select and provision the right AWS compute environment for each task. Rather than being limited to a single execution backend, the agent can choose from a spectrum of compute options — from lightweight AgentCore Runtime microVMs for quick interactive tasks, to CodeBuild for CI/CD pipelines, to EC2 instances for long-running or specialized workloads, to ECS Fargate for containerized services.

The system implements a "compute router" pattern: the agent analyzes the task requirements (duration, resources, tools needed, persistence, cost sensitivity) and selects the optimal execution environment. Each environment is provisioned on demand, used for the task, and cleaned up when done.

This builds on the existing OpenClaw AWS Extension (OpenClaw Gateway on Fargate, Bedrock provider, AgentCore Gateway with Lambda tools) and extends it with a pluggable execution backend that bridges OpenClaw's ACP (Agent Client Protocol) to multiple AWS compute services.

## Glossary

- **Execution Environment**: An AWS compute resource provisioned on demand to execute agent tasks (shell commands, code, deployments, builds)
- **Compute Router**: The decision layer that analyzes task requirements and selects the optimal execution environment
- **ACP Backend**: An implementation of OpenClaw's `AcpRuntime` interface that delegates execution to a remote AWS compute service
- **Runtime Template**: A pre-configured execution environment definition (container image, IAM role, installed tools, resource limits)
- **Session**: A stateful execution context within an environment, with persistent filesystem and environment variables
- **Ephemeral Environment**: An environment that is created for a task and destroyed after completion
- **Persistent Environment**: An environment that survives across tasks (e.g., a development EC2 instance the agent maintains)

## Requirements

### Requirement 1: Pluggable Execution Backend

**User Story:** As an operator, I want the agent to execute tasks on the most appropriate AWS compute service, so that quick tasks use lightweight microVMs and complex tasks use purpose-built environments.

#### Acceptance Criteria

1. THE system SHALL implement OpenClaw's `AcpRuntime` interface as a custom plugin that routes execution to AWS compute services
2. THE system SHALL support at least four execution backends: AgentCore Runtime, AWS CodeBuild, EC2, and ECS Fargate
3. WHEN the agent needs to execute a task, THE compute router SHALL analyze the task and select the optimal backend based on task characteristics
4. THE system SHALL allow the agent to explicitly request a specific backend when it has enough context to make the decision
5. THE system SHALL fall back to AgentCore Runtime as the default backend when no specific requirements are identified

### Requirement 2: AgentCore Runtime Backend (Quick Interactive Tasks)

**User Story:** As an operator, I want quick interactive tasks (shell commands, code testing, file operations) to run on AgentCore Runtime microVMs, so that they start in seconds and cost only for active execution time.

#### Acceptance Criteria

1. THE AgentCore Runtime backend SHALL create sessions via `InvokeAgentRuntime` for reasoning tasks and `InvokeAgentRuntimeCommand` for deterministic shell commands
2. THE backend SHALL support persistent filesystem across session stop/resume for multi-step tasks
3. THE backend SHALL use pre-configured Runtime templates with common tools (AWS CLI, CDK, Node.js, Python, Git)
4. THE backend SHALL auto-cleanup idle sessions after a configurable timeout (default: 15 minutes)
5. THE backend SHALL support streaming output back to the agent in real time
6. WHEN a task exceeds AgentCore Runtime's 8-hour session limit, THE system SHALL notify the agent to consider a different backend

### Requirement 3: CodeBuild Backend (CI/CD and Build Tasks)

**User Story:** As an operator, I want build and deployment tasks to run on AWS CodeBuild, so that the agent can leverage managed build environments with Docker support, caching, and artifact management.

#### Acceptance Criteria

1. THE CodeBuild backend SHALL create on-demand build projects with custom buildspec definitions generated by the agent
2. THE backend SHALL support custom Docker images as the build environment (e.g., CDK-ready image, data science image)
3. THE backend SHALL stream build logs back to the agent in real time via CloudWatch Logs
4. THE backend SHALL store build artifacts in S3 with the `agent-` prefix for traceability
5. THE backend SHALL support builds up to 8 hours (CodeBuild maximum)
6. THE backend SHALL support environment variables injected from Secrets Manager for secure credential handling
7. WHEN a build completes, THE backend SHALL return the build status, artifacts location, and any outputs to the agent

### Requirement 4: EC2 Backend (Long-Running and Specialized Workloads)

**User Story:** As an operator, I want the agent to provision EC2 instances for tasks that need specific hardware (GPUs, high memory), long-running processes, or custom OS configurations.

#### Acceptance Criteria

1. THE EC2 backend SHALL launch instances from pre-approved AMIs with the `agent-` name prefix
2. THE backend SHALL support instance type selection based on task requirements (CPU, memory, GPU)
3. THE backend SHALL execute commands on the instance via SSM Session Manager (no SSH keys needed)
4. THE backend SHALL auto-terminate instances after task completion or a configurable maximum lifetime (default: 4 hours)
5. THE backend SHALL support persistent EBS volumes that can be reattached across instance launches for stateful workloads
6. THE backend SHALL apply a permission boundary to the instance role that prevents IAM, Organizations, and Billing actions
7. WHEN an instance is running, THE backend SHALL stream command output back to the agent via SSM

### Requirement 5: ECS Fargate Backend (Containerized Services)

**User Story:** As an operator, I want the agent to deploy containerized services on ECS Fargate when a task requires a long-running service (API server, worker process, scheduled job).

#### Acceptance Criteria

1. THE ECS Fargate backend SHALL create task definitions from agent-specified container images and configurations
2. THE backend SHALL deploy services with the `agent-` prefix in the existing VPC
3. THE backend SHALL support health checks and auto-restart for deployed services
4. THE backend SHALL return the service endpoint (ALB URL, task IP) to the agent after deployment
5. THE backend SHALL support service updates (new container image, environment variable changes) without full redeployment
6. WHEN the agent requests service teardown, THE backend SHALL stop the service and clean up associated resources

### Requirement 6: Compute Router (Intelligent Environment Selection)

**User Story:** As an operator, I want the agent to automatically select the best execution environment based on task characteristics, so that I don't have to specify the compute backend for every request.

#### Acceptance Criteria

1. THE compute router SHALL analyze task text and metadata to determine: estimated duration, resource requirements (CPU, memory, GPU), required tools, persistence needs, and cost sensitivity
2. THE compute router SHALL apply the following default routing rules:

| Task Characteristic | Recommended Backend |
|---|---|
| Quick command (< 5 min), interactive | AgentCore Runtime |
| Code testing, file operations | AgentCore Runtime |
| CDK deploy, CloudFormation stack creation | CodeBuild |
| Docker image build | CodeBuild |
| CI/CD pipeline execution | CodeBuild |
| GPU workload (ML training, inference) | EC2 (GPU instance) |
| Long-running process (> 8 hours) | EC2 |
| Custom OS/kernel requirements | EC2 (custom AMI) |
| Persistent API service | ECS Fargate |
| Batch data processing | AgentCore Runtime or CodeBuild |

3. THE compute router SHALL allow the agent to override the default selection with an explicit backend choice
4. THE compute router SHALL log every routing decision with the task description, selected backend, and reasoning for observability
5. THE compute router SHALL estimate cost before provisioning and include the estimate in the routing decision

### Requirement 7: Security and Isolation

**User Story:** As an operator, I want all execution environments to be isolated and secured, so that the agent cannot escalate privileges or access resources outside its scope.

#### Acceptance Criteria

1. ALL execution environments SHALL use IAM roles with permission boundaries that deny IAM, Organizations, Account, and Billing actions
2. ALL agent-provisioned resources SHALL use the `agent-` name prefix for identification and scoped IAM policies
3. THE system SHALL enforce a maximum concurrent environment limit (default: 3) to prevent runaway provisioning
4. THE system SHALL enforce a maximum monthly cost budget for agent-provisioned compute (configurable, default: $100)
5. THE system SHALL log all environment provisioning and teardown events to CloudWatch with the operator's Telegram user ID
6. WHEN the agent attempts to provision an environment that would exceed the budget or concurrency limit, THE system SHALL deny the request and notify the operator

### Requirement 8: Environment Lifecycle Management

**User Story:** As an operator, I want execution environments to be automatically cleaned up after use, so that I don't accumulate idle resources and unexpected costs.

#### Acceptance Criteria

1. THE system SHALL track all active execution environments in a DynamoDB table with creation time, last activity, and estimated cost
2. THE system SHALL run a cleanup Lambda every 30 minutes that terminates environments exceeding their maximum lifetime
3. THE system SHALL send an SNS notification when an environment is auto-terminated
4. THE system SHALL support manual environment termination via Telegram command (e.g., "shut down all running environments")
5. WHEN the Gateway container restarts, THE system SHALL reconcile its state with actual running environments and clean up orphans

### Requirement 9: Self-Extending Capabilities

**User Story:** As an operator, I want the agent to be able to create new tools and register them dynamically, so that its capabilities grow over time based on what it builds.

#### Acceptance Criteria

1. WHEN the agent builds a new Lambda function, THE system SHALL offer to register it as a new tool on the AgentCore Gateway
2. WHEN the agent creates a new API, THE system SHALL offer to add it as an OpenAPI target on the Gateway
3. THE system SHALL maintain a registry of agent-created tools in DynamoDB with metadata (name, description, creation date, usage count)
4. THE agent SHALL be able to list, describe, and remove its self-created tools
5. WHEN the agent creates a new tool, THE system SHALL update the Gateway target configuration without requiring a CDK redeploy

### Requirement 10: Observability and Cost Tracking

**User Story:** As an operator, I want visibility into what environments the agent is running, what they cost, and what they're doing.

#### Acceptance Criteria

1. THE system SHALL emit CloudWatch metrics for: active environments count, environment provisioning latency, task execution duration, and estimated cost per environment
2. THE system SHALL maintain a cost ledger in DynamoDB that tracks per-environment and per-day compute costs
3. THE system SHALL provide a daily cost summary via Telegram (or on-demand via "how much have my agents spent today?")
4. THE CloudWatch dashboard SHALL include widgets for execution environment usage alongside the existing agent metrics
